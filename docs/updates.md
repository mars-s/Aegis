# Signed app updates

Aegis uses the official Tauri 2 updater with a minisign-signed `Aegis.app.tar.gz`
and a static `latest.json`. It checks about 10 seconds after launch, at most
once every six hours. The native app menu offers **Check for Updates…** and
**Restore Previous Version…**. Manual checks report when the app is up to date;
passive checks only display a dialog when an update is available. Errors from
manual checks appear in a native dialog; passive errors go to the app log.
Release notes are trimmed and shown with the install confirmation.

The public key is compiled from `src-tauri/updater/pubkey.txt`. An empty file or
`REPLACE_WITH_TAURI_SIGNER_PUBLIC_KEY` disables checks and labels the menu item
**Updates are not configured**. A configured but invalid key fails verification.
The plugin requires a config field before applying its builder key, so Aegis
supplies a minimal config in memory. No updater config or fake key is stored in
`tauri.conf.json`. No updater commands have webview permissions, including the
remote `host-ui` capability. The existing UI hot-swap mechanism is independent.

Every downloaded artifact must pass the plugin's signature verification before
installation. A missing signature, wrong key or changed artifact fails closed.
Only versions newer than the running version are offered, using the plugin's
default comparator. The manifest itself is not signed, so HTTPS protects its
metadata. In the manifest, `signature` is the base64 encoding of the entire
minisign signature file text, and the compiled key is the base64 encoding of the
entire minisign public key file text. Use the Tauri signer's output directly.

## Channels and local feeds

`DATA` is the existing Aegis data folder, normally
`~/Library/Application Support/Aegis`, or `AEGIS_DATA` when set. With Aegis closed,
set `DATA/updater.json` to `{"channel":"stable"}` or `{"channel":"nightly"}`.
Missing or invalid settings default to stable. The app preserves the channel and
records `last_check` as Unix seconds, including failed checks. Manual checks
ignore this throttle. Changing channel does not allow a downgrade.

The endpoints share one base constant, `RELEASE_BASE` in `src-tauri/src/updater.rs`:

| Channel | Endpoint |
| --- | --- |
| stable | `https://github.com/mars-s/Aegis/releases/latest/download/latest.json` |
| nightly | `https://github.com/mars-s/Aegis/releases/download/nightly/latest.json` |

**The repository is private. Unauthenticated update requests will return 404
today.** Before enabling distribution, move the release assets and manifest to a
public releases repository or Cloudflare R2, update `RELEASE_BASE` and ensure the
manifest's artifact URLs are publicly accessible too. Do not embed a GitHub token
in the app.

`AEGIS_UPDATE_ENDPOINT` replaces the channel endpoint for testing. All endpoints
and artifact URLs must use HTTPS, except explicitly overridden HTTP feeds on
`127.0.0.1` or `localhost`. Only that override enables the plugin's insecure
transport option. Signature verification remains mandatory. A local test feed
still needs an artifact signed with the configured key. Test keys generated by
the Rust tests live only in memory.

## Release runbook

1. Generate a release key on a trusted machine:

   ```sh
   npx @tauri-apps/cli signer generate -w ~/.tauri/aegis.key
   ```

   Keep the private key and password in a secure backup outside the repository.
   Put the generated public key, in Tauri's encoded format, in
   `src-tauri/updater/pubkey.txt`. Never commit a private key.
2. Add repository secrets `TAURI_SIGNING_PRIVATE_KEY` (the private key file's
   contents) and `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` (the chosen password).
   Apple secrets are optional. The workflow uses Tauri's default ad-hoc signing unless
   `APPLE_SIGNING_IDENTITY` is provided. A supplied identity must already be
   available in the runner's keychain; certificate provisioning and notarisation
   are outside this prototype.
3. Bump the version in both `src-tauri/tauri.conf.json` and
   `src-tauri/Cargo.toml`, and refresh the package entry in Cargo.lock. Run:

   ```sh
   node scripts/check-release-version.mjs v0.3.0
   ```

   Substitute the intended version. Commit the release changes, then tag that
   commit `v<version>` and push the tag. The workflow rejects mismatched versions.
   Manual dispatch builds the selected ref and creates a draft `v<version>` too.
4. The macOS job explicitly targets `aarch64-apple-darwin`, stages the runtime, builds the app, generates the updater
   archive and signature, and uploads `latest.json` to a draft release. It also
   uploads `Aegis-<version>-macos-arm64.zip` for manual installation.
   Updater artifacts are enabled only through `tauri.release.conf.json`, merged
   by CI. A normal local `npm run build` needs no updater signing key.
5. Inspect the draft's notes, version, manifest URLs, signature and assets. Test
   a signed update on a Mac using a local feed or public staging location. Publish
   the draft as the latest stable release when ready.

The workflow has no main-branch trigger. A future nightly workflow should be
manual dispatch only, maintain a rolling `nightly` prerelease, and publish an
increasing version in its manifest. The current workflow only publishes stable
versioned drafts.

The currently installed app has no updater. Users need a **one-time manual
installation** of a build containing this updater and the real public key before
automatic updates can work. A placeholder-key build also needs a manual install
to enable updating.

## Key loss and rotation

Losing the private key means existing installations cannot verify newly signed
builds. Recover the secure backup, or distribute a new app and public key by
manual installation. A compromised key needs the same recovery if a trusted
transition can no longer be delivered.

For planned rotation, first publish a bridge release signed with the old private
key but compiled with the new public key. Then sign later releases with the new
private key. This prototype trusts one key at a time. Keep the old-signed bridge
available on a separate feed for users who missed it, or have those users install
manually. Replacing the public key alone strands existing installations.

## Rollback and macOS limits

The primary rollback is server-side: publish a **higher version** that reverts
the faulty change. Republishing a lower version will not be offered.

Before installation on macOS, Aegis resolves the running `.app` bundle and uses
`/usr/bin/ditto` to copy it to
`DATA/updates/previous/Aegis-<current version>.app`. Only the two newest completed
backups are kept, ordered by backup time. A failed backup prevents installation.
The restore menu is enabled only when a backup exists. After confirmation it
moves the running bundle aside, moves the newest backup into its place, removes
the moved-aside bundle, stops the agent host and restarts. If the backup move
fails, it attempts to put the running bundle back. Bundle moves require the data
folder and installed app to share a filesystem, and the app location must be
writable. An unfinished `.app.restoring` path blocks another restore and is
reported for manual recovery. Restoring the app does not restore user data or
any separately hot-swapped UI. Check compatibility before using an older build.

Ad-hoc signing is not notarisation. Gatekeeper may require manual approval.
The ad-hoc signature changes each build, so macOS may ask again for microphone,
camera and speech permissions after an update. A stable signing identity,
self-signed or Developer ID, fixes that identity change. Developer ID with
notarisation is the normal distribution path. Exercise native dialogs, backup,
installation, permission prompts and restart on a real Mac before shipping.
